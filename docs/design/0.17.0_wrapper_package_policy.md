# 0.17.0 Wrapper Package Policy

This is a docs-only package and discovery policy record for possible future
Python or Rust wrapper stabilization. It does not start wrapper implementation,
publish packages, change the public C ABI, or add package-manager recipes.

## Decision

Continue prototype-only wrapper status until package, discovery, compatibility,
CI, and ownership policy is explicitly accepted for a specific wrapper line.

The post-`v0.16.0` wrapper public diagnostics smoke proved that both prototypes
can reach the stable 190-symbol C ABI. It did not prove that either wrapper is
ready for publication. The remaining risk is distribution policy: how a stable
wrapper finds or carries `ruckig_c`, how it rejects unsupported C ABI versions,
who owns package artifacts, and which platforms are release-gated.

## Discovery Candidates

| Strategy | Candidate behavior | Status |
| --- | --- | --- |
| External installed shared library | Wrapper loads `ruckig_c.dll`, `libruckig_c.so`, or `libruckig_c.dylib` from an explicit environment variable, platform loader path, or installed package location. | Preferred for continued prototype smoke; not accepted for stable publication until search order and error behavior are frozen. |
| Vendored shared library | Wheel or crate ships a built `ruckig_c` shared library for each supported platform. | Deferred; requires artifact ownership, signing/checksum policy, platform matrix, and release automation. |
| Static linking | Rust or a native Python extension links `ruckig_c` statically. | Deferred; incompatible with the current Python `cffi` ABI-mode prototype and requires a different Rust crate/build policy. |

Platform-specific discovery questions remain open:

- Windows: DLL directory precedence, `PATH` behavior, and whether a wrapper may
  load from a package-private directory.
- Linux: `LD_LIBRARY_PATH`, `rpath`/`RUNPATH`, distro library names, and whether
  a wheel may vendor `libruckig_c.so`.
- macOS: `DYLD_LIBRARY_PATH`, `@loader_path`, codesigning/notarization impact,
  and whether a package-private `.dylib` is acceptable.

## Wrapper Model Comparison

Python currently uses `cffi` ABI mode. That keeps the wrapper thin and makes the
prototype easy to test against an already-built shared library, but it requires
a runtime shared-library discovery contract before stable publication.

Rust currently links an already-built local library through the alpha wrapper
build script. That is suitable for repository smoke tests, but stable crate
publication needs a decision between external library discovery, vendored
artifacts, or source/build integration.

Neither prototype currently owns a stable package namespace, package metadata,
binary artifact lifecycle, or cross-platform installer behavior.

## Compatibility Policy Candidates

Any stable wrapper implementation must define all of the following before code
work starts:

- Minimum supported C ABI version.
- Whether wrappers accept newer C ABI versions or require an exact stable
  version match.
- Unsupported-version failure behavior and error text.
- Mapping from `ruckig_result_t`, public diagnostics scope/code enums, and
  tracking diagnostics into wrapper-level types.
- Behavior when the shared library is missing, unloadable, or lacks an expected
  symbol.

Default recommendation for the next implementation proposal is exact stable C
ABI version acceptance for the first published wrapper line, with explicit
failure on missing symbols or mismatched version metadata. A looser minimum
version policy can be reconsidered after one published wrapper line exists.

## Ownership And CI Requirements

A stable wrapper line must name owners for:

- Wheel or crate contents and release artifacts.
- Platform support matrix.
- Binary build provenance and reproducibility notes.
- CI jobs that exercise package install/import/link behavior.
- Release checklist evidence for package publication.
- Post-release support for broken package installs.

These decisions are not accepted yet. Until they are accepted, Python and Rust
remain prototype-only smoke targets.

## Next Allowed Routes

A later implementation plan must explicitly choose one route:

- Python-first stabilization after accepting wheel/shared-library discovery and
  Python package ownership.
- Rust-first stabilization after accepting crate linking/build policy and crate
  ownership.
- Dual-wrapper stabilization after accepting the additional CI and release
  burden for both wrappers.
- Continued prototype-only status.

No route is selected by this policy record.

## Non-Goals

- No stable Python wrapper API.
- No stable Rust wrapper API.
- No wheel, source distribution, or crate publication.
- No package-manager recipe.
- No public C ABI expansion.
- No edit to `include/ruckig_c/ruckig.h`.
- No ABI allowlist or public-symbol exception change.
- No version metadata, tag, GitHub Release, or workflow change.
